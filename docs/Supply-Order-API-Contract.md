# Контракт заказов на поставку

## Назначение

Документ фиксирует целевой контракт desktop-клиента для полного цикла поставки:

```text
Этап контракта → Потребность/В наличии → Формирование заказа → Оплата → Поступление
```

Задействованные модели:

- `StageOrder` — единая позиция поставки;
- `Order` — заказ поставщику;
- `Stage` — этап контракта, для которого требуется позиция;
- `IsecurityTool` — материал, оборудование или программное обеспечение;
- `OrderStatus` — статус заказа;
- `Contragent` — поставщик.

`StageOrder` не является вложенной редактируемой частью `Stage` или `Order`. Создание и изменение выполняются отдельными mutation-запросами модели `StageOrder`.

## Основные инварианты

1. `StageOrder` может существовать без `order_id`, если позиция заведена для этапа до формирования заказа.
2. `StageOrder` может существовать без `stage_id`, если позиция относится к заказу, но не распределена по этапу.
3. У позиции должна быть хотя бы одна предметная привязка: `stage_id` или `order_id`.
4. Привязка потребности к заказу выполняется обновлением `order_id` существующей позиции. Создавать копию позиции нельзя.
5. `list_key` обязателен в любом create/update запросе `StageOrder`.
6. Mutation payload содержит только идентификатор записи, измененные поля и `list_key`.
7. Read-model объекты `stage`, `order` и `isecurity_tool` не отправляются обратно в mutation payload.
8. Mutation-ответ используется только как подтверждение операции и источник `id`. Полная строка для UI перечитывается read-пресетом.
9. `Order.order_number` допускает `null`.
10. Новый заказ для первичного сбора предложений создается со статусом `Запрос цены`, `order_status_id = 0`.

## `StageOrder`

### Назначение

`StageOrder` представляет одну позицию материала или СЗИ на протяжении всего процесса. Одна и та же запись сначала может быть потребностью этапа без заказа, затем получить `order_id` и стать позицией заказа.

### Mutation-поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `id` | integer | только update | Идентификатор позиции |
| `list_key` | string | всегда | Ключ изменения записи |
| `stage_id` | integer/null | условно | Этап контракта |
| `order_id` | integer/null | условно | Заказ поставщику |
| `isecurity_tool_id` | integer | да | Материал/СЗИ |
| `severity` | integer/null | нет | Состояние позиции поставки |
| `price_cost` | number/null | нет | Цена единицы |
| `amount` | number/null | нет | Количество |
| `cost` | number/null | нет | Сумма позиции |
| `description` | string/null | нет | Описание |
| `priority` | integer/null | нет | Порядок отображения |

Условная обязательность: хотя бы одно из полей `stage_id` и `order_id` должно быть заполнено.

### Состояние поставки

`StageOrder.severity` использует единый контракт во всех таблицах, фильтрах и редакторах:

- `0 — Потребность` — позицию необходимо заказать;
- `1 — В наличии` — позиция уже есть на складе и включать ее в заказ не требуется;
- `2 — На контроле` — позиция требует контроля;
- `3 — Не согласовано` — поставка позиции еще не согласована;
- `4 — Поставлено` — товар передан контрагенту и больше не числится на складе.

### Создание из этапа

Контекст workflow: `ForStage(stageId)`.

Пример формы payload:

```json
{
  "model": "StageOrder",
  "StageOrder": {
    "list_key": "generated-uuid",
    "stage_id": 7,
    "isecurity_tool_id": 8,
    "severity": 0,
    "amount": 2,
    "description": "Требуется для этапа"
  }
}
```

`order_id` не отправляется, пока заказ не сформирован.

### Создание из заказа

Контекст workflow: `ForOrder(orderId)`.

```json
{
  "model": "StageOrder",
  "StageOrder": {
    "list_key": "generated-uuid",
    "order_id": 12,
    "stage_id": 7,
    "isecurity_tool_id": 8,
    "price_cost": 15000,
    "amount": 2,
    "cost": 30000
  }
}
```

`stage_id` в этом контексте может быть `null`.

### Привязка потребностей к заказу

```json
{
  "model": "StageOrder",
  "StageOrder": {
    "id": 101,
    "list_key": "existing-list-key",
    "order_id": 12
  }
}
```

Rails update родительского `Order` со `stage_orders_attributes` не поддерживает привязку ранее
не связанных позиций и отвечает `400 Bad Request`. Поэтому множественная операция store
последовательно обновляет каждую выбранную `StageOrder` минимальным payload из `id`, `list_key`
и целевого `order_id`. `StageOrder` поддерживает аудит изменений, поэтому `list_key` нельзя
опускать.

При формировании нового заказа клиент сначала создает `Order` со статусом `0`, получает его `id`,
а затем выполняет тот же цикл update `StageOrder`. Операция не является атомарной: при ошибке
последовательность останавливается на первой неуспешной позиции, уже выполненные updates не
откатываются.

## Read-пресеты `StageOrder`

### `StageOrder.order`

Назначение: зависимая таблица позиций выбранного заказа.

Подтвержденные поля:

- `id`;
- `list_key`;
- `stage`, включая `stage.id`, `stage.name`, `stage.contragent`;
- `isecurity_tool`;
- `severity`;
- `price_cost`;
- `amount`;
- `cost`;
- `description`;
- `priority`;
- `created_at`;
- `updated_at`.

Запрос ограничивается `order_id` выбранного заказа.

### `StageOrder.stage`

Назначение: полное представление позиции в ветке `Поставка` выбранного этапа.

Подтвержденный контракт содержит все данные позиции:

- `id`;
- `list_key`;
- nullable `order` с номером, поставщиком и статусом;
- `isecurity_tool`;
- `severity`;
- `price_cost`;
- `amount`;
- `cost`;
- `description`;
- `priority`.

`StageOrder.stage` не содержит `stage`, потому что родительский `Stage.card` уже задает контекст этапа. Клиент не должен собирать update payload из read-модели: состояние редактора извлекается из строки, а payload формируется отдельным builder.

## `Stage`

### `Stage.card`

`Stage.card` содержит:

```json
{
  "stage_orders": []
}
```

Поле `stage_orders` имеет тип `StageOrder.stage[]` и включает все позиции выбранного этапа — как еще не привязанные к заказу, так и уже включенные в заказ.

Ветка `Поставка` первоначально наполняется из `Stage.card.stage_orders`. Дополнительный запрос списка `StageOrder` при открытии уже загруженной карточки этапа не требуется. После mutation позиции необходимо перечитать актуальный `Stage.card` и обновить ветку, чтобы изменения были видны во всех рабочих контекстах.

Статус связанного заказа в ветке `Поставка` отображается badge и фильтруется локально через
multi-select с опциями справочника `OrderStatus`. Локальная фильтрация обязательна, поскольку
источником строк остается уже загруженный массив `Stage.card.stage_orders`.

В диалоге этапа ОЗИ комментарии и поставка представлены двумя корневыми ветками `TreeView`.
Ветка комментариев содержит единственные экземпляры редактора нового комментария и истории,
ветка поставки переиспользует `StageSupplyView`, `StageSupplyStore` и `StageSupplyEditWorkflow`.
При навигации между этапами содержимое обеих веток перестраивается для нового `stage.id`.
Диалог имеет рабочую ширину 1100 px; сводка и редакторы этапа остаются в центрированном
контейнере шириной не более 820 px, а дерево поставки использует всю доступную ширину.

## Таблица `Потребность`

До появления отдельного компактного preset таблица использует `StageOrder.card` как наиболее полное
представление позиции. Начальный запрос содержит:

```json
{
  "model": "StageOrder",
  "preset": "card",
  "filters": {
    "order_id__null": true
  },
  "sorts": [
    "isecurity_tool_id asc"
  ]
}
```

Фильтр `order_id__null = true` и сортировка `isecurity_tool_id asc` являются начальными настройками
table platform. `StageOrder.card` обязан возвращать `id` и `list_key`; отсутствие любого из полей
является нарушением read-контракта.

Для товарных колонок объект `isecurity_tool` также содержит `unit` и `kind`. `unit` отображается
в колонке `Ед.`, а `kind` используется для отображения, сортировки и multi-select фильтра колонки
`Тип товара`; API-фильтр имеет форму `isecurity_tool.kind__in`.

## `Order`

### Назначение

`Order` объединяет позиции поставки для работы с поставщиком и отражает движение заказа от запроса цены до поступления.

### Mutation-поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `id` | integer | только update | Идентификатор заказа |
| `order_number` | string/null | нет | Номер счета или заказа |
| `contragent_id` | integer | да | Поставщик |
| `order_status_id` | integer | да | Статус заказа |
| `cost` | number/null | нет | Общая сумма |
| `requested_at` | date/null | нет | Дата запроса |
| `ordered_at` | date/null | нет | Дата заказа |
| `payment_at` | date/null | нет | Дата оплаты |
| `received_at` | date/null | нет | Дата поступления |
| `description` | string/null | нет | Описание |

Новый заказ создается с `order_status_id = 0`. `order_number` заполняется позднее и не участвует в клиентской валидации обязательных полей.

### `Order.item`

Компактное представление для lookup-сценариев. Формат поля `name` должен корректно обрабатывать `order_number = null`; правило форматирования принадлежит backend.

### `Order.list`

Основной preset таблицы `/orders`. Он не должен включать массив `stage_orders`.

Ожидаемые поля:

- `id`;
- `order_number`;
- `supplier`;
- `status`;
- `cost`;
- `requested_at`;
- `ordered_at`;
- `payment_at`;
- `received_at`;
- `description`;
- `created_at`.

### `Order.card`

Полная карточка одного заказа. Используется перед редактированием заказа и в сценариях, которым действительно нужны расширенные данные.

Карточка может включать `stage_orders: StageOrder.order[]`, но основной список `/orders` не должен загружаться через `Order.card`.

### `Order.stage`

Компактная информация о заказе внутри позиции этапа:

- `id`;
- nullable `order_number`;
- `supplier`;
- `status`.

## `OrderStatus`

`OrderStatus.id` задается клиентом при создании и не изменяется после создания.

Зафиксирован системный статус:

| ID | Наименование | Назначение |
|---:|---|---|
| `0` | `Запрос цены` | Первичный статус формируемого заказа |

Поля справочника:

- `id`;
- `name`;
- `order`;
- `description`.

Поле сортировки справочника называется `order`, не `priority`.

## Отображение в desktop-клиенте

### Ветка этапа `Поставка`

В дереве каждого этапа:

```text
Этап
├── Параметры этапа
├── Комментарии
└── Поставка
```

Ветка владеет `StageSupplyStore` и зависимым `CbsTableView`, отображающим `Stage.card.stage_orders`. Таблица является полноценным selectable-представлением с командами добавления, редактирования и удаления. Ее содержимое визуально компенсирует служебный отступ leaf-элемента `TreeView`; геометрия остальных веток дерева не изменяется.

Создание и редактирование коммерческой позиции выполняются через `StageSupplyEditWorkflow` и компактный `StageSupplyEditFlyout`. Flyout не открывает вложенный `ContentDialog` и содержит только:

- `Наименование` — autocomplete по `IsecurityTool.card`;
- `Количество`;
- `Важность` — обычный enum `Dropdown` с полным единым набором `Потребность`, `В наличии`,
  `На контроле`, `Не согласовано` и `Поставлено`.

При выборе СЗИ клиент копирует `IsecurityTool.default_cost` в `StageOrder.price_cost`. При изменении количества вычисляется:

```text
cost = price_cost × amount
```

Mutation payload формирует `StageSupplyEditPayloadBuilder`; Flyout не сериализует запрос самостоятельно. После create/update/delete карточка этапа перечитывается, а таблица получает актуальный массив `stage_orders`.

Если `order.order_number` заполнен, коммерческий редактор считает позицию уже заказанной: изменение и удаление блокируются. DELETE адресуется по обязательному `StageOrder.id`; нарушение этого контракта приводит к исключению до запроса и не запускает повторное чтение `Stage.card`.

### Экран `/orders`

Master-detail:

- верхняя таблица — `Order.list`;
- нижняя таблица — `StageOrder.order`, отфильтрованная по выбранному `order_id`.

Статус заказа отображается badge и фильтруется через multi-select `status_id__in` с опциями
справочника `OrderStatus`. Состав заказа разрешено изменять только при
`status.id == 0 && order_number == null`. При `status.id != 0 || order_number != null`
добавление и отвязка позиций блокируются.

Редактор существующей позиции доступен при любом статусе заказа. При `status.id != 0`
он работает в ограниченном режиме: доступны только `severity`, `priority` и `description`;
этап, товар, цена, количество и сумма заблокированы и не включаются в mutation payload.
Ограниченный режим строится только из `StageOrder.order` и не загружает справочники этапов
или СЗИ. Полный режим предварительно загружает этапы с `status_id__not_eq = 5`; закрытые
этапы в выбор не входят. СЗИ не загружаются полным каталогом: после первой введенной буквы
редактор с задержкой 300 мс выполняет `IsecurityTool.card` с `name__cnt`, лимитом 25 и отменой
предыдущего поискового запроса.

Удаление позиции из заказа означает не DELETE `StageOrder`, а update с обязательными `id`,
`list_key` и `order_id = null`; после этого позиция снова попадает в `Потребность`. Операция
требует подтверждения во flyout. При удалении всего заказа store сначала последовательно
отвязывает тем же способом все его позиции и только после полного успеха вызывает DELETE `Order`.

### Экран `Потребность`

Отдельная таблица `/needs` показывает `StageOrder.card` с начальным фильтром непривязанных позиций.
Начальный multi-select фильтр `Важность` содержит значения `0`, `2` и `3`, поэтому позиции
`1 — В наличии` и `4 — Поставлено` не участвуют в формировании поставок по умолчанию,
но могут быть включены пользователем через фильтр.

State-кнопка `Отображать заказы` управляет фильтром связи с заказом. В выключенном состоянии
действует `order_id__null = true`, а колонки `Номер счета`, `Поставщик` и `Статус заказа` скрыты.
Во включенном состоянии фильтр снимается и эти колонки отображаются, позволяя получить общую
выборку позиций для дальнейшей выгрузки.
Колонки `Статус этапа` и `Статус заказа` используют multi-select фильтры
`stage.status_id__in` и `order.order_status_id__in`. Опции регистрирует специализированный host:
`StageStatus` формируется общим provider допустимых статусов этапа, `OrderStatus` загружается
из справочника статусов доставки. Общий `TablePageStore` не владеет этими источниками опций.
Множественное выделение используется для двух операций:

- создать новый `Order` со статусом `0 — Запрос цены` и выбранным поставщиком;
- добавить выбранные позиции в существующий `Order`.

Обе операции принадлежат `StageOrderNeedsStore`. Для существующего заказа store сразу выполняет
последовательность update `StageOrder`; для нового сначала создает `Order`, затем запускает тот же
цикл. После полного успеха таблица перечитывается; при активном начальном фильтре связанные позиции
исчезают.

Общий редактор `StageOrder` открывается для последней позиции в порядке множественного выделения.
Редактирование существующей позиции допускается и без внешнего контекста заказа или этапа; требование
контекста сохраняется только для создания новой записи. Удаление выполняется как DELETE `StageOrder`
после подтверждения и разрешено только при `stage.id = null`. Проверка принадлежит
`StageOrderNeedsStore`; позиция, связанная с этапом, не может быть удалена из общей таблицы.

## Роли

### Коммерческий отдел

- создает и редактирует позиции этапа в ветке `Поставка`;
- указывает материал, количество и состояние поставки;
- видит дальнейший заказ и его статус через ту же запись `StageOrder`.

### ОЗИ

- просматривает общую таблицу потребностей;
- формирует заказы;
- привязывает существующие позиции к заказам;
- меняет статус и реквизиты заказа;
- видит результат в `/orders` и в ветке этапа `Поставка`.

## Неопределенные части backend-контракта

1. Будущее имя и поля компактного preset общей таблицы `Потребность`, который заменит временное
   использование `StageOrder.card`.
2. Поведение formatter-поля `Order.item.name` при `order_number = null`.
